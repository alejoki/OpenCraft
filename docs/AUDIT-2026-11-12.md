# OpenCraft repository audit

- **Date:** 2026-11-12
- **Commit:** `632962c` — "feat: Release Hardening and Codebase Cleanup"
- **Version:** 0.2.1
- **Scope:** whole repository (no folder was named)
- **Method:** `cargo clippy --locked --all-targets -- -D warnings` (clean),
  `cargo test --locked` (all pass). Source read: README, Cargo.toml, CI and
  release workflows, all entry points, save writer/reader, streaming manager,
  physics, inventory and container transfers, config registry and watcher,
  pack decode/validation, audio, arrows, and the test tree.

## What this repo does

OpenCraft is a single-player voxel game written in Rust: it generates an
infinite deterministic world, streams and meshes chunks near the player,
renders with wgpu, simulates survival, mobs, combat and village structure,
and saves worlds to local `.mcvx` files. It also loads user-editable TOML
config, content packs and texture packs from disk.

**Load assumed:** one player, one process, one save file, 60+ frames per
second, chunks streaming in and out as the player walks. No network, no
multi-user, no server. So "scale" here means frame time and long sessions,
not concurrent writers.

## Must fix

### 1. A failed save is invisible while you play

`src/main.rs:4585-4589` (F5), `src/main.rs:7076-7084` (autosave),
`src/main.rs:1837-1841` (shutdown)

- **What this is:** There are four save triggers: F5, the background autosave,
  Save and Quit, and window close. Each one writes the same world file.
- **Problem:** Save and Quit shows "could not save world: …" when the write
  fails. F5 and the autosave throw the error away:
  `if save_current_world(...).is_ok() { badge }` has no failure branch, and
  `poll_autosave` only checks `result.is_ok()`. Scenario: the disk fills up.
  F5 appears to do nothing. The autosave fails silently. The player keeps
  playing, then closes the window — that last save is
  `let _ = save_current_world(...)`, also dropped — and every edit since the
  last good save is gone, with no message ever shown. The world stays marked
  unsaved, but nothing retries it.
- **Fix:** In the two places that drop errors while a HUD exists, set the
  existing gameplay notice slot to `format!("could not save world: {err}")`
  (the same slot break-rejections use), exactly like the Save-and-Quit arm at
  line 3578. Leave the dirty flag as it is. About 4 lines.
- **If we skip it:** A player whose disk is full or whose save directory became
  read-only loses the session's work believing it was saved.

## Should fix

### 2. Nothing saves on a timer, only when a chunk unloads

`src/world/session.rs:271-273`, called from `src/main.rs:5688`

- **What this is:** `autosave_due` returns true only when `unloaded` is
  non-empty — i.e. only when a chunk leaves the streaming radius.
- **Problem:** Build inside a 16×16 area for an hour, never cross a chunk
  border, and no autosave ever fires. If the process then dies (crash, kill,
  power loss — not a clean window close, which does save), the whole session is
  lost. The only protection is an F5 the player remembers to press.
- **Fix:** Keep the same single-writer worker; only change the trigger. Track
  the last successful save instant and call `queue_autosave` when
  `now - last_save > 60s && world.has_unsaved_changes()`, without requiring an
  unload. Roughly 10 lines in the Playing frame path.
- **If we skip it:** Long stationary builds are protected only by manual saves,
  which is a worse durability story than the one the release notes describe.

### 3. `settings.toml` and `config/*.toml` lack the file guards that saves and packs already have

`src/settings/mod.rs:366` and `:165`, `src/config/mod.rs:836`

- **What this is:** Saves reject non-regular files and cap size before reading
  (`open_save_file`, `src/world/persistence.rs:3021`). The 0.2.1 notes say packs
  got the same treatment. Settings and config did not: they call
  `fs::read_to_string` directly, and config checks the length from metadata but
  never `is_file()`.
- **Problem:** A pipe (FIFO) named `settings.toml` reports length 0 and then
  blocks the read until some writer opens it — the game hangs at launch before
  a window appears, despite the loader's comment saying it "never blocks
  launch". A multi-gigabyte `settings.toml` (or a symlink to one) is read fully
  into memory and can exhaust RAM. The same applies to
  `preserve_unparseable_settings`, which uses an unbounded `fs::read` on every
  settings save.
- **Fix:** One shared guard `read_small_text(path, MAX)` that does `metadata`,
  `is_file()`, length cap (1 MiB, same as config) and then reads. Use it for
  settings load, settings backup-read, and config files. About 15 lines,
  deletes the ad-hoc reads.
- **If we skip it:** The failure mode is a hang or OOM at startup, which is the
  hardest kind to diagnose from a user report.

### 4. The atomic writes do not flush the directory

`src/world/persistence.rs:2954-2972`, `src/settings/mod.rs:281-291`

- **What this is:** Both writers do the right thing for the file: write a
  sibling `.tmp`, `sync_all()` it, then rename over the target. That is a
  "durable file" but not yet a "durable name".
- **Problem:** The rename itself lives in the parent directory. Without `fsync`
  on that directory, a power loss right after the game reports a successful
  save can leave the directory entry pointing at the old file (or at the temp
  file). The content was synced; the name change was not. Result: the last save
  silently disappears and the previous state loads. Two copies of this pattern
  also mean a fix to one misses the other.
- **Fix:** One shared helper `atomic_write(path, bytes)` that does temp + file
  sync + rename + parent-directory `sync_all()` (skip the directory sync where
  opening a directory handle is not possible, i.e. Windows). Delete both
  private copies.
- **If we skip it:** A crash in the wrong millisecond loses the save the player
  was just told was written.

### 5. The frame-budget tests never run automatically

`.github/workflows/ci.yml:66-67`, `src/world/manager.rs:3786`, `:3950`,
`tests/autosave_budget.rs:268`, `tests/village_frame_budget.rs:75`

- **What this is:** The only tests that measure frame time — streaming, village
  generation, and the autosave snapshot — are `#[ignore]`d because they need a
  release build. CI and the release workflow both run plain
  `cargo test --locked`, which skips them.
- **Problem:** This is exactly the kind of regression that passes every other
  test: frame work moves back onto the main thread, the autosave snapshot
  doubles, the village wave slows down. Nothing fails. The budget numbers in
  `docs/RELEASE-NOTES-0.2.1.md` are therefore only ever checked by hand.
- **Fix:** Add one CI step:
  `cargo test --locked --release --test autosave_budget -- --ignored --nocapture`.
  It is a single test, and it protects the budget the release notes publish.
  Add the village one as a second step if time allows.
- **If we skip it:** The published performance contract is unenforced; a future
  milestone can regress it silently.

### 6. No GPU adapter means a Rust panic message, not an explanation

`src/render/context.rs:78-101`

- **What this is:** Window and GPU setup uses `expect` for the surface, adapter
  and device, and then indexes `caps.formats[0]`.
- **Problem:** A downloadable release started on a machine wgpu cannot drive
  (old Intel GPU, remote desktop, missing Vulkan/GL) prints
  `thread 'main' panicked at … Failed to find suitable GPU adapter` plus a
  backtrace hint and exits. Every other external failure in this codebase is a
  typed, user-readable outcome; this one is the first thing a new player can
  hit. An empty `caps.formats` also panics on the index.
- **Fix:** Match on the results, print one line
  (`opencraft: no compatible GPU found (requires Vulkan, Metal, DX12 or OpenGL 3.3)`)
  and `exit(1)`; handle the empty-format case with a clear message. Localized
  to this constructor.
- **If we skip it:** Unsupported-hardware users get a crash they cannot
  interpret, and the bug tracker gets reports that say only "panicked".

### 7. Slot and cell drawing maths is copied three times

`src/ui/chest.rs:228-260, 320-350`, `src/ui/inventory.rs:677-700, 850-875`,
`src/ui/hud.rs:209-212`

- **What this is:** `rect_quad`, `inset`, `cell_fill`, `cell_inset`,
  `count_origin` and `push_cell_labels` are byte-for-byte identical between the
  chest and inventory screens (the chest comment even says it "mirrors the
  inventory screen"), and the hotbar has a third, already-slightly-different
  version of the count origin (fixed 2 px vs a dynamic inset).
- **Problem:** These are the rules that make item counts sit in the same place
  in every slot grid. They must change together and nothing tests that they
  agree — each screen's tests only check its own numbers. The hotbar has
  already drifted from the other two.
- **Fix:** Move the six shared helpers into `src/ui/quad.rs` (already the shared
  quad home) as `pub(crate)`, have all three call sites use them, and delete the
  copies. About 45 lines deleted, no new module.
- **If we skip it:** The next slot-size or padding change lands in two screens
  and misses the third.

## Nice to have

### 8. `main.rs` is 31,314 lines, of which 23,866 are tests

`src/main.rs:7449`

- **What this is:** The whole application shell is 7,448 lines; the rest of the
  file is one `#[cfg(test)] mod tests`. Much of it tests pure helpers that live
  in the library (`ui::inventory`, `commands`, `ui::screens`).
- **Problem:** The bin test target compiles the entire application, and a reader
  looking for the event loop scrolls past 24k lines of tests. The library
  modules that own the behaviour have their own test modules, so this is partly
  duplicated coverage in a harder place to run.
- **Fix:** Move the tests for library-owned helpers next to those helpers and
  keep only app-shell tests here. No new code, just relocation.
- **If we skip it:** Nothing breaks; the file stays the slowest place in the
  repo to navigate.

### 9. `autosave.rs` still suppresses dead-code warnings for an outdated reason

`src/world/autosave.rs:15-20`

- **What this is:** `#![cfg_attr(not(test), allow(dead_code))]` with a comment
  saying the module is "complete ahead of its frame-loop wiring".
- **Problem:** The wiring landed in M016/S02; every item is now used. The
  `allow` means a future genuinely unused worker method in the save path will
  not be reported by clippy.
- **Fix:** Delete the attribute and the stale comment, and let the compiler
  enforce it.
- **If we skip it:** Dead code can accumulate in the module that writes save
  files.

## Verdict

Healthy. The domain code is unusually careful — transactions, bounds,
fail-closed parsing, single-writer saves, substepped physics and arrows. Fix 1
first: it is the only finding that loses player data under a realistic failure.

**Lean:** -45 lines, -0 dependencies possible. All 13 direct dependencies are
used; the removals come from the duplicated slot helpers and the second copy of
the atomic write.
