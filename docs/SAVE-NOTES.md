# Save and Release Notes

**Who this is for.** You have a world saved by an earlier version of OpenCraft and you want to open it in this build.

**What to do first.** Make a copy of the save file and put it somewhere the game will not touch.

Loading an old world and then saving it upgrades the file to the current format. Older builds cannot open the upgraded file. The copy is your way back.

This build writes save format version 9. A version 8 file loads through the same reader with no config notice and stays playable. If the gameplay config it was saved with has changed, or its schema has changed, the game shows exactly one non-blocking notice after the world is open. A malformed v9 tail fails closed instead of loading a half-understood file.

After that, load your world. Choose Load Game from the main menu, or launch straight into it with the save path. Expect the same seed, the same blocks you changed, new terrain everywhere else, and a calendar that starts at day 0. The rest of this page explains each of those.

## What changed in this release

- The world now has four biomes, a real sea level, and oceans filled with water.
- The world has a calendar: a day counter and a configurable season length.
- Seasons change surface blocks, and weather adds rain or snowfall.
- New worlds pick a safe land spawn instead of spawning at the world origin.
- The save file now carries the world's game mode (Survival or Creative), your health, hunger, and breath, and the contents of every chest you placed.
- Survival now has health, hunger, and breath, with fall, drowning, and starvation damage, regeneration, death, and respawn.
- Apples and bread restore hunger through a hold-to-eat action; apples drop from oak leaves.
- Hoes till grass and dirt into Farmland; Wheat grows through four stages and pauses in Winter; Bread is crafted from three Wheat.
- Chests hold 27 slots, and surface-ruin LootChests carry deterministic per-seed loot.
- The item vocabulary now includes leather, raw porkchop, raw beef, rotten flesh, bones, arrows, swords, and bows. An older build cannot read a save that carries them, and an older save can never contain them.
- Saves now store content names instead of numeric ids. A sorted, save-local content table makes every block, item, and tool name readable; unknown-but-well-formed names load as deterministic placeholders; and a pack-identity plus FNV-1a digest tail reports a changed content stack without ever blocking the load.
- Saves now record the config schema and an effective-value digest of the gameplay tuning that wrote them. A version 8 save still loads silently because it carries no config record; a changed config or schema shows one non-blocking notice, and the next save writes version 9.
- Recipe edits now report a narrower restart reason than other pack-content edits. An edit confined to `[[recipes]]` or `[[recipe_patches]]` shows `recipe changed`; a mixed or other content edit shows `content changed`. The live registry stays frozen in both cases: quit, relaunch, and load the same save, which then shows the one-time `content definitions changed` notice and uses the new recipe. Texture and `[builtin_icons]` edits still apply live.
- New worlds created from the New Game screen default to Survival; Creative remains selectable there, and fresh worlds launched from the command line default to Creative.
- Old worlds keep every block you edited. Everything you never edited is regenerated by the new terrain generator.

## What a save file contains

A world save is a single file with the `.mcvx` extension, kept in the `saves/` folder next to the game's settings. The world list shows each file as a row, using the file name and the time it was last changed. A world the game cannot read stays in the list marked "(cannot load)" instead of silently disappearing. A save file larger than 256 MiB is treated as an invalid save and stays listed as "(cannot load)" instead of being read into memory.

The file stores:

- The world seed.
- Your edits: every block you broke or placed, with its position and the block that replaced the generated one.
- Crop stages, which are ordinary chunk edits. Crop growth progress is not saved.
- Your player: position, view direction, game mode, fly toggle, health, hunger, breath, selected hotbar slot, and render distance.
- Your inventory: hotbar slots, main inventory, cursor stack, and any unfinished crafting grids, which may now include leather, raw porkchop, raw beef, rotten flesh, bones, arrows, swords, and bows. An older build cannot read a save that carries them, and an older save can never contain them.
- The contents of every chest you placed, stored by position as 27 slots.
- The world clock: the time of day and the number of whole days elapsed.
- The calendar: the day index and the length of one season (stored as `day_index` and `season_length_days`).
- The live mobs: each mob's kind, feet position, facing, and remaining health, written after every chest record.
- The content table: the sorted names of every block, item, and tool the save references. The tail after the mobs records the pack folders, versions, and FNV-1a digest of the content stack that wrote it.
- The config tail: the config schema version and a 64-bit FNV-1a digest of the effective gameplay values the world was saved with, written after the content identity tail.

The file does not store terrain. Terrain is produced from the seed every time a chunk is needed. That is why a save is small, and it is why terrain can be regenerated on load.

Saving writes a temporary file first and then renames it over the old one. An interrupted save therefore cannot leave a half-written world; you keep the previous good file.

## Loading a save from an older version

This build reads every version 1-8 save through the same load path. A version 8 file is the important case: it has no config record, so it loads with no config notice and remains playable. If the effective config differs from the one the file was saved with, or the config schema differs, the game shows one non-blocking notice after the world is open. Malformed input fails closed with a named error instead of being guessed at.

### The calendar starts at day 0

Saves written before the calendar existed carry no day or season data. They load with:

- Day index 0.
- A season length of one game day.
- Noon, if the save is old enough to predate time-of-day storage.

Day 0 starts in the season chosen by your world seed. Different seeds start in different seasons, so an old world may resume in Spring, Summer, Autumn, or Winter. That is determined by the seed, not by the date you load it.

The calendar is stored the next time the world is saved. Use quick save, the pause menu's Save and Quit, or simply close the window.

### An older save loads as Creative

Saves written before version 6 carry no game mode and no vitals. They load as:

- Creative mode, so flying and building work as they did in the release that wrote them.
- Full health, hunger, and breath.
- No chest records, because earlier versions did not store chest contents.

The mode is chosen when a world is created and cannot be changed afterwards. A migrated world therefore keeps its Creative mode for the rest of its life, and a newer build reads it as Creative every time. The file is upgraded on the next save, as described below.

### An older save loads with no mobs

Saves written before version 7 carry no mob records. They load with an empty mob list, and the world resumes without the animals or hostiles that a version 7 save would have preserved. New mobs spawn from the world seed as usual, so the world is playable immediately; it simply starts with no persisted mobs. The mob tail is written the next time the world is saved.

### Terrain you never edited is regenerated

Only your edits are in the file. On load, the game regenerates every chunk from the seed and then reapplies your edits on top.

- Every block you changed stays changed.
- Every other block is whatever the current terrain generator produces at that position for that seed.
- This is deliberate, not a migration bug. The old terrain was never stored, so there is no copy of it to preserve.

The visible consequences for an old world:

- Familiar landmarks may be gone.
- Your base may now sit on a cliff, inside a mountain, or beside a new ocean.
- New oceans, beaches, mountains, trees, and surface ruins can appear around what you built.
- The world is still the same seed, so it is still deterministic: the same build and seed always produce the same new terrain.

If your saved position is now inside solid ground and you are in walk mode, press F to fly out, then press F again to return to walking.

### The save is upgraded when you save

On the next save, the world is written in the current format and gains the calendar fields. The current format cannot be read by older builds. If you might return to an older build, keep the copy you made first.

Loading a world does not rewrite its file by itself. The upgrade happens only when the world is next saved.

The previous release wrote save format version 8; this build writes version 9. Version 6 added the game mode, health, hunger, breath, and one record per chest with its position and 27 slots. Version 7 appended the mob tail: a `u32` mob count followed by one 19-byte record per mob — kind (`u8`), feet `x`/`y`/`z` (`f32` each), facing (`yaw` as `f32`), and remaining health (`u16`). Version 8 replaces every numeric content id with a `u16` index into a sorted, save-local content string table in the header, and appends a pack-identity plus FNV-1a digest tail. Version 9 appends a 10-byte config tail after that: a `u16` config schema and a `u64` digest of the effective gameplay values. A version 5 file has no v6 tail, which is exactly why it loads as Creative with full vitals and no chest records. Version 1-7 files load through the frozen legacy decoder; version 8 files load through the same content-table decoder as version 9 and carry no config record (`saved_config=None`). The next save writes version 9. A version 9 file whose config schema is newer than this build still loads: an unknown nonzero schema is a notice, not a rejection. A file that claims a save version newer than this build understands is rejected instead of guessed at.

A scripted demo save pins the concrete v9 layout. An edit-free save with an empty inventory is 179 bytes: the version word is at offset 4, the content table at offset 36 holds a zero name count (4 bytes), the mob count is at 153, the v8 pack-identity + digest tail fills 157..169, the v9 config schema fills 169..171, and the config digest fills 171..179. The general empty-inventory v9 offsets are 134 (calendar), 142 (mode), 143 (health), 145 (hunger), 147 (air), 149 (chest count), and 153 (mob count). The `--demo-survival` run is edit-free and its `inventory_kept=true` path keeps one Apple and one Stick, so its content table holds `apple` and `stick` (18 bytes) and the save is exactly 201 bytes: calendar at 156, mode at 164, health at 165, hunger at 167, air at 169, chest count at 171, mob count at 175, pack count at 179, the 12-byte pack tail at 179..191, the config schema at 191..193, and the config digest at 193..201. The `--demo-combat` save is exactly 317 bytes: its 72-byte content table (seven names) starts at 36, its mob count of 2 is at 253, the two surviving hostile records occupy 257..295, the 12-byte pack-identity + digest tail fills 295..307, and the 10-byte config tail fills 307..317. That demo earns the wood sword, the pig and cow drops, the bow and arrows the ranged stage fires, and the skeleton's bone, arrows, and rare bow, so the inventory section is part of the layout: the save holds the two surviving hostile records at 11 and 14 health together with the earned eight inventory stacks (a wood sword at 59 durability, a wood bow worn to 56 by its three shots, a second full 59-durability bow from the skeleton's rare drop, 3 arrows, raw porkchop, raw beef, leather, and one bone). A change to what a mob drops, what the demo crafts, or how many shots it fires changes the length, so the pinned numbers are measured from a real run rather than derived. The version 8 witnesses are historical migration detail: an edit-free v8 save was 169 bytes with the pack tail ending at 169, the survival v8 save was 191 bytes with its pack tail at 179..191, and the combat v8 save was 307 bytes with its pack tail at 295..307; those files carry no config record. Version 7's older witnesses are historical migration detail too: an edit-free v7 save was 153 bytes with the mob count at 149, the survival v7 save was 159 bytes with the mob count at 155, and the combat v7 save was 218 bytes with the mob count at 176. Arrows in flight are never persisted — in-flight projectiles are ephemeral exactly like mob knockback — so version 7 gained no arrow tail, version 8 added only the content table and digest tail, and version 9 added only the config tail. Ordinary content saves are variable-length because chunk edits shift the tail. Unknown block, item, mode, chest, or mob data and water fail closed; an unknown but well-formed content name becomes a placeholder instead.

The damage cause shown on the Death screen (`Cause: Zombie`, `Cause: Fall`, `Cause: Drowning`, `Cause: Starvation`, `Cause: Skeleton arrow`) is ephemeral and is never written to a version 9 save, so a dead save that is reloaded shows `Cause: Unknown`. The version 9 offsets above are unchanged by that: the cause is session state, not a wire field.

A damaged or unreadable save is not repaired by the game. When the game is launched directly into a world and the file cannot be read, that launch starts a new world at the same path instead of failing. Keep the copy before experimenting.

## Save version 8: names, the content table, and placeholders

Version 8 is the modding foundation. The save no longer stores numeric block, item, or tool ids. Every persisted content reference is a `u16` index into a sorted, save-local content string table:

- The table starts in the header, immediately after the render distance. It is a `u32` name count followed by each name as a `u16` UTF-8 byte length and its bytes, in ascending name order.
- Built-in names are unqualified (`stone`, `apple`, `wood_sword`). Pack content uses its namespaced id (`mymod:ruby_ore`).
- Every saved block edit, inventory stack, cursor stack, crafting-grid cell, chest slot, and item reference points at a table index instead of an enum or raw id. Two saves of the same world always write the same sorted table.
- The table is save-local: index 3 in one file means nothing in another file. That is what keeps a save readable by name when pack load order changes.

### Unknown names become placeholders

When a saved name is well-formed but absent from the loaded content stack, the load does not fail and does not drop the reference. It appends a deterministic placeholder definition and resolves the saved index to it:

- An unknown block name becomes a placeholder block. It is solid, unbreakable, and drops nothing. Placeholder blocks use the built-in checker texture and stay in the world exactly where they were saved.
- An unknown generic item name becomes a placeholder item. It is movable and stackable in the inventory, and uses the reserved transparent checker icon layer.
- An unknown pack tool degrades to a count-one placeholder item, keeping its pack-tool kind on the wire. Restoring the pack returns it as the live tool at its full authored durability: wear is not carried through the placeholder.
- The saved names are preserved across a second save. Removing a pack never rewrites the world to a different id: restoring the pack resolves the same names to the real definitions again.
- A name that is malformed, uses a reserved namespace (`opencraft`, `builtin`, `minecraft`) but does not exist, or refers to a liquid is not a placeholder: the whole load fails closed with a named error.

### Pack identity and the digest tail

After the mob records, a version 8 save ends with:

- A `u32` pack count, then one record per pack sorted by folder: the folder name (length-prefixed) and an optional length-prefixed version.
- A `u64` FNV-1a digest of the content definitions and authored asset keys. The digest excludes built-in definitions, asset bytes, and diagnostics, so a built-in-only stack writes the empty-stack digest.

The tail is metadata, not a checksum of the world bytes: it describes which content wrote the save and what that content looked like. A version 9 save continues after this tail with the config tail described in the next section.

### The changed-stack warning is non-blocking

On load, the game compares the saved pack list and digest with the current stack. If they differ, it shows one readable notice after the world is already open and playable. Typical messages name a missing pack, an added pack, a changed pack version, `content definitions changed`, or `N saved content names are unavailable and render as placeholders`. The notice never blocks the load and is never written back to the save; it is consumed once and then cleared.

### What happens to version 1-7 saves

Versions 1-7 keep their existing migration path. They are read by the frozen legacy decoder, which understands every older layout; no placeholder is created because those files contain no names. The world opens normally with the older data it has: no mobs before version 7, Creative with full vitals before version 6, and day 0 before the calendar. The next save writes version 9: the same world data is named into a fresh content table, every reference gets an index, the pack identity plus digest tail is added, and the effective config schema and digest follow it. Version 8 saves already have the content table and pack tail; they load with `saved_config=None`, show no config notice, and gain the config tail on their next save.

The measured version 8 witnesses are in the layout paragraph above. Older builds cannot read a version 8 file; make a copy before loading an old world if you might return to an older release.

## Save version 9: config schema and digest

Version 9 adds one thing after the existing content identity tail: a 10-byte config tail. It is written after the `u32` pack count, the pack records, and the `u64` content digest, so no existing byte moves.

- The first two bytes are the config schema version (`u16`).
- The next eight bytes are a `u64` FNV-1a digest of the effective gameplay values.

The digest hashes values, not file bytes. It covers the config schema and every effective value in lexicographic key order. Comments, whitespace, file order, and formatting do not move it; editing a value does. A value that fails validation is folded in as its default, so the digest describes what the game will actually use, not what a file intended. The config tail is separate from the content identity: a changed pack stack and a changed gameplay config are reported independently.

### What happens on load

A version 8 save has no config tail, so it loads with `saved_config=None` and never shows a config notice. A version 9 save carries the schema and digest that wrote it:

- Same schema and same digest: no notice.
- Same schema, different digest: one notice, `config changed since this world was saved`.
- Different schema, any digest: one notice, `config schema changed since this world was saved`.

The notice is non-blocking: the world is already open and playable when it appears. It is computed once at load and consumed once. If a content notice is also present, the two are joined into one message with `"; "`, content first. The menu-background editor discards both notices instead of showing them (a background scene must not nag), and no frame or live-reload path re-derives them. A tuning edit therefore cannot produce a fresh warning every time the config changes.

The writer records the validated effective metadata it is about to save with. A hand-built or stale schema is rejected before the first output byte, so a mismatched schema never reaches the wire. On load, a zero schema, a truncated v9 tail, or trailing bytes after it fail closed with `InvalidConfigMeta`; a nonzero schema from a future build is accepted as data and becomes the schema-change notice, never an `UnsupportedVersion` error. Re-saving writes version 9 with the current meta, so a reload under the same config is silent.

The headless `--demo-save-v9` proof loads a v8 file, reports the silent config leg, re-saves it as version 9, and reloads it under matching and changed configs. Its sibling `--demo-restart` proves the restart boundary instead: one run writes a fixture save, a recipe edit happens between runs, and a second run on the same save reports the one-time `content definitions changed` notice and previews and crafts the edited recipe. Both headless seams run in debug and release and never open a window.

## The new terrain, briefly

The generator now builds four biomes from the seed:

- **Plains** and **Forest** share the middle height range, with grass, dirt, and oak trees. Forest is denser.
- **Mountains** rise above a fixed mountain threshold and show bare stone with snow near their peaks.
- **Ocean** is every column below the fixed sea level. Ocean basins are filled with water and have a sand seabed. Basins deepen away from the shore, so the deepest oceans hold 24 blocks of water.

Sand beaches sit where the land meets the water line. Deterministic surface ruins appear on some plains and forest land. All of this comes from the seed alone.

The old generator produced a single grassland. The current generator reads the same seed but shapes it differently, which is why an old world's unedited terrain looks new.

## Water

Water is part of world generation. It is not a normal block you can own or move.

- Every column below sea level is filled with water when its chunk is generated.
- Water is static. It does not flow, spread, or refill a hole you dig into a seabed.
- Water cannot be mined, carried, placed, or held in the hotbar. It is never an item.
- Water is never written into a save. The save format rejects water in stored edits, so a tampered file fails to load rather than producing a corrupt world.
- A generated ocean is recreated from the seed on every load, so it costs nothing in the file. You can fill individual water cells by placing blocks into them, and those placements are saved as normal edits, but there is no way to drain or remove an ocean.

You can swim in it. In walk mode, water applies drag and gravity: an idle body sinks away from the surface, and holding Jump rises back up. There is no automatic surface lock and no separate dive key. Movement is slower than on land. Fly mode behaves as it always has; water does not change it.

The water surface is translucent, and the view shifts to underwater fog while your eye is submerged.

## Spawning in a new world

A fresh world no longer spawns at the world origin. The origin can be open ocean after the terrain rewrite, so the game searches outward from it for a safe column and uses the first one it finds.

A safe column is:

- Dry land at least two blocks above sea level.
- Clear of tree trunks and overhanging leaves.
- Clear of surface ruins.

The search is bounded and deterministic. The same seed always picks the same column. In the rare case that no safe column exists within the bound, the game stops with a message naming the seed and the search radius instead of dropping you into water or inside a wall.

New worlds created from the New Game screen default to Survival: they spawn walking and cannot fly. Choose Creative on that screen to keep the previous flying and building behavior. A fresh world launched from the command line defaults to Creative; pass `--creative` or `--survival` to pick its mode (the last flag wins). A loaded world always keeps the mode it stored, so those flags do nothing to it. In Creative, press F to drop into walk mode or fly again; in Survival, F does not enable flight.

Loading an existing save never moves you. Your saved position is restored exactly, even when the regenerated terrain around it has changed.

## Seasons and weather

The calendar is a pure function of three things: the day index, the season length, and the world seed. Nothing depends on your computer's clock, so the same save always resumes in the same season and the same weather.

- Day 0 starts in the season chosen by the seed.
- A new season begins every time the day index crosses the season length.
- The New Game screen offers season lengths of 1, 2, 4, and 8 days. The default is 1 day.
- A save file can carry any season length from 1 to 365 days. A stored value outside that range is treated as 1 day instead of breaking the world.
- One game day lasts 20 real minutes at normal speed. Development flags can accelerate this, but they do not change how time is stored.

Season boundaries change how the world looks:

- **Winter** turns the grass surface of plains and forest into snow. Trees keep their trunks and branches and stand bare through the winter; they no longer disappear with the green surface.
- **Spring**, **Summer**, and **Autumn** keep the grass surface and the full canopy; trees stay green until Winter arrives.
- Leaves are the only seasonal part of a tree. Trunks and branches are generated identically in all four seasons.
- Beaches, ocean seabeds, and the altitude snow caps on mountains look the same all year.

The change is applied to chunks in a bounded wave rather than all at once, so the game keeps running while the world changes around you. Every block you edited still wins over the seasonal surface.

Weather is decided per day from the seed and the day index:

- Most days are clear.
- Spring, Summer, and Autumn days can bring rain.
- Winter days can bring snowfall, never rain.

Weather is presentation only. It never changes blocks and is never saved. Because it is derived from the seed and day, reloading a save shows the same weather for the same day.

Season length is stored in the save. A launch flag that sets season length applies only when creating a new world; a loaded world always keeps the length it stored.

## Survival, health, and death

Survival is the default for worlds created from the New Game screen. It is a real ruleset, not a label:

- The vitals are health 20, hunger 20, and breath 300. The HUD shows hearts, hunger, and air bubbles; bubbles appear while you are submerged or below full breath.
- A fall of up to 3 blocks is free. Past that, each whole block of fall distance costs 1 health.
- While your head is submerged, breath drains at 20 points per game second, so a full lung lasts 15 seconds. Once it is empty, drowning costs 2 health per game second.
- Hunger drains 1 point per 30 game seconds. At zero hunger, starvation costs 1 health per 4 game seconds.
- At hunger 18 or above, you regenerate 1 health per 4 game seconds, and each point healed costs 1 hunger.
- Creative is immune: it takes no damage, loses no hunger or breath, and keeps its flight toggle.
- The mode is chosen when the world is created and cannot be changed later.

When health reaches zero, the Death screen appears. **Respawn** restores full health, hunger, and breath at the deterministic spawn and keeps your inventory exactly as it was. **Quit** saves the world and returns to the main menu. A save file that is already at zero health opens the Death screen when loaded, so it can be resolved the same way.

## Food

- Apples drop from oak leaves deterministically: one in eight leaf blocks, decided by the world seed and the leaf's position.
- Hold Right Click with apples or bread in the selected hotbar slot to eat. A progress bar fills over 1.6 seconds. Releasing the button or moving cancels the meal without consuming the food.
- Eating is refused at full hunger with "Cannot eat while full". An apple restores 4 hunger; bread restores 6.
- Bread is crafted from three Wheat in a row at a crafting table.

## Farming

- Wood, Stone, and Iron hoes are tools with durability. Right-click the top face of a grass or dirt block to till it into Farmland; side faces are refused.
- Right-click Farmland with Wheat Seeds to plant a crop.
- Wheat has four stages, and each stage takes 60 game seconds. Winter pauses growth. Growth progress is not saved, so a reloaded crop resumes from its current stage.
- Mature wheat harvested with Left Click yields 1 Wheat and 2 Wheat Seeds. Immature wheat returns 1 Wheat Seed.
- Crop stages are ordinary chunk edits. They survive save/reload and chunk unload/regeneration.
- Bread is three Wheat in a row at a crafting table.

## Chests and ruins

- A Chest is crafted from eight Oak Planks in a ring (a 3x3 pattern with an empty center) at a crafting table.
- A chest has 27 slots; the chest screen shows them next to your 36-slot player inventory.
- The chest screen is whole-stack only. Left click moves a whole stack between the chest and your inventory; right click is inert in the chest screen. The standalone inventory panel keeps its right-click split/place-one behavior; the chest screen does not.
- E or Escape closes the chest screen.
- Contents are stored per chest position and persist across save and reload.
- Breaking a chest requires room in your 36 inventory slots for all of its contents plus the Chest item itself. If there is not enough room, the break is refused with "Not enough inventory space to break the chest" and nothing changes.
- Surface ruins can contain a LootChest. Its contents are deterministic for the world seed and the ruin, so the same save always yields the same loot. A LootChest you have emptied stays recorded as empty and never re-rolls. Breaking it yields one ordinary Chest.
- There are no item-drop entities. Blocks and crops go straight into your inventory, and death keeps your inventory.

## Mobs, spawning, and combat

Four mobs can live in a world: Pig and Cow are passive, Zombie and Skeleton are hostile. Spawning is deterministic for a seed and obeys these rules:

- The safe radius is 24 blocks around the player and around the world spawn; no mob spawns inside it.
- New mobs appear in a ring 24-48 blocks from the player.
- A mob more than 96 blocks from the player is removed.
- At most 32 mobs exist at once, and at most 4 of them occupy any one 32-block region, counted across loaded and unloaded chunks.
- Passive mobs need full sky light on a grass block and spawn during the day.
- Hostile mobs need sky light 7 or less at any hour, or full sky light at night.
- A hostile on the lit surface loses 1 health every 0.5 seconds; cover or water at its feet stops the burn.

Version 7 introduced the mob tail, and version 9 keeps the same fixed 19-byte record: kind (1 byte), feet x/y/z (4 bytes each), facing yaw (4 bytes), and health (2 bytes, little-endian). Loading is fail-closed: an unknown kind, a non-finite position or facing, health above the kind's maximum, a duplicate kind-and-position record, or an out-of-bound count rejects the whole save instead of skipping a record. Saves from versions 1-6 load with zero mobs and gain the mob tail only when saved again as version 9.

The `--demo-combat` capstone produces a measured 317-byte version 9 save. Version 9 is at offset 4, the 72-byte content table occupies 36..108, the mob count of 2 is at 253, the two 19-byte records fill 257..295, the 12-byte pack-identity + digest tail fills 295..307, and the 10-byte config tail fills 307..317: a Zombie at 11 health and a Skeleton at 14 health. The rest of the layout is the earned inventory described above, so the pinned size is measured from a real run rather than derived.

Arrows in flight, mob knockback, and the damage cause are ephemeral. They are live-session state only and are never written to a save; version 7 added no arrow or knockback tail, version 8 added only the content table and digest tail, and version 9 added only the config tail. Creative rules follow the effective mode, so a Creative player is never targeted or damaged by a mob and one-shots it with drops intact, including while editing the menu background.

## The menu background is a save too

The rotating scenery behind the main menu is a real world save, kept separately from your playable worlds at `saves/background/background.mcvx`. It uses the same format as any other save: seed, your block edits, position, inventory, clock, and calendar.

- **Edit Background** on the main menu enters that world as a normal gameplay session. Build, mine, and fly with the usual controls, then use the pause menu's Save and Quit.
- The menu camera sits at the saved player's eye position, so the menu looks out from the spot where you left the editor. The sideways drift and fixed downward tilt are unchanged; the saved view direction is not used.
- The menu sky follows that save's time of day, and the menu terrain follows its calendar season. Both are frozen while you sit on the menu; they advance only while you are editing. Weather stays clear on the menu.
- The file lives in a subdirectory of `saves/`, so it never appears in the Load Game list and cannot be deleted from there. No background path ever writes a playable world's save.
- If the file is missing, the built-in deterministic scenery appears and nothing is written until your first edit. If the file is unreadable, the built-in scenery appears with a message on the main menu and the file is left untouched; editing the background then saves over that unreadable file the next time you use Save and Quit.
- To reset the background, delete `saves/background/background.mcvx`. The next launch shows the built-in scenery; the next successful edit creates a fresh file.
- If a background save fails while editing, the editor stays open with the reason on the pause screen so the work is not silently lost. Closing the window while editing saves the background like any other gameplay session.

Edit Background always runs Creative rules without rewriting the stored mode. Press **C** in the editor to open the same searchable Creative palette and grant building blocks; the palette reads the session registry, so pack changes apply on the next world load.

## What did not change

These guarantees survived the terrain rewrite:

- **The seed still determines everything.** The same build, seed, and calendar always generate the same terrain, trees, ruins, caves, ores, and water.
- **Trees render in full, including near the shoreline.** A tree whose trunk, branches, or canopy cross a vertical chunk edge keeps every block, so trees are never cut short halfway up a slope. A tree standing on a steep bank can still have its lower leaves hidden by the hillside in front of it, which is ordinary terrain occlusion rather than clipping.
- **Your edits always win.** They are reapplied over freshly generated terrain when a chunk loads, unloads, or changes season.
- **Caves still carve stone only below the surface.** They never open the surface or remove the ground you stand on.
- **Ores still appear only in their depth bands**, in stone, as before.
- **Bedrock still forms the bottom of the world.** You cannot fall out of it.
- **The save is still one atomic file**, and player state and inventory from the previous release load without loss.

## Checklist after loading your old world

1. Make the backup copy before you load, if you have not already.
2. Load the world and note which season day 0 gives you.
3. Save once (quick save, Save and Quit, or close the window) to write the calendar into the file.
4. Survey your builds. Your edited blocks should be exactly where you left them; the terrain around them may be new.
5. If you are stuck inside blocks, press F and fly out.
6. Check your inventory, hotbar, and any unfinished crafting grids. They load as before.
7. Look around for new oceans and beaches if you want to try swimming.
8. If the result is not what you want, replace the world's file with the copy you made. There is no in-game undo for terrain regeneration.

## Limits and fine print

- There is no terrain migration tool. The saves-only-edits design means there is nothing to migrate: the old terrain was never in the file.
- Saves that predate the expanded inventory keep their hotbar contents; the newer inventory slots start empty. A save old enough to predate hotbar storage keeps no items.
- A save with an out-of-range render distance is rejected rather than guessed at.
- Hand-editing a save file is not supported. Corrupt or unknown data either fails the load with a named error or falls back to a safe default, depending on the field.
- The menu background's viewpoint is wherever you stood when you last saved the editor. Building across that spot can put geometry in front of or around the camera; move before saving to reframe it.
- Development flags for demos and smoke tests (`--new`, `--seed`, `--save`, `--time-scale`, `--season-length`, `--demo-days`, `--demo-swim`, `--demo-survival`, `--demo-content`, `--demo-combat`, `--demo-ui`, `--demo-presentation`, `--demo-crafting`, `--demo-worldgen`, `--demo-village`, `--demo-capture`, `--demo-palette`, `--demo-save-v9`, `--demo-restart`, `--check-config`, `--creator-trace`, `--validate-pack`) are not part of the normal player flow. They change how a launch runs (some demos advance the calendar and save before exiting), not how an existing save file is interpreted. `--demo-survival` and `--demo-content` are bounded scripted demo switches that save and exit for the smokes. `--demo-ui` prints three pinned `ui_demo:` digest lines and exits before creating a world, save, or window; any world flags on the same launch are ignored. The four content-pack digests (`--demo-presentation`, `--demo-crafting`, `--demo-worldgen`, `--demo-palette`) read the selected pack stack and print deterministic structural lines without opening a window; `--demo-presentation` and `--demo-crafting` use `--save` only as the path for their fixture save, and the other world flags are ignored. `--demo-save-v9` loads a v8 save, writes the derived v9 file next to it without touching the input, and prints the load, resave, and matching-config legs for the migration proof; it never opens a window. `--demo-village` reads only `worldgen/` and prints the catalog fingerprint, a pinned plan, and identical-cell proofs for shuffled order, one-chunk-at-a-time, empty-catalog and outside-the-bounds generation; it never opens a window or writes a save. `--demo-capture <dir>` builds an isolated in-memory world, drives the real two-corner capture state machine to write one fixed house below `<dir>/prefabs/`, re-parses the written bytes, runs the real worldgen validator over `<dir>`, then writes `<dir>/villages/capture_demo.toml` and proves socket capture plus a village/road placement from the captured prefab; it never opens a window or touches settings, packs, or a save, and a missing directory value exits 2 with `error: --demo-capture requires a directory`. `--demo-restart` writes a two-run, same-save restart proof: the first run creates a fixture save, a recipe edit happens between runs, and the second run prints the save and load legs, including the one-time `content definitions changed` notice. `--validate-pack` reads one pack folder and prints a per-entry report without starting a world or touching settings, saves, or any pack file. `--creative` and `--survival` select the mode of a fresh world only (the last flag wins); a loaded world keeps its stored mode. The mob/combat capstone is reproduced outside the game with `bash scripts/combat_smoke.sh`; set `SMOKE_PROFILE=release` to run the same assertions against the release binary.
- `--check-config` and `--creator-trace` are debug-build creator tools. A release build rejects them before any startup work: it prints exactly `check-config: dev build only` or `creator-trace: dev build only` and exits 1 without reading settings, packs, a save, or `config/`. Normal config and pack loading still runs in release, and `--demo-save-v9`, `--demo-restart`, and `--validate-pack` remain available there.
- There are no item-drop entities and no death drops; death keeps your inventory. In Creative, press **C** to open the searchable Creative palette: it lists every non-placeholder built-in and pack block, item, and tool, filters by name, display name, or namespace, and grants a full authored stack into the hotbar. Placeholders never appear in the palette, and pack changes apply on the next world load because the session registry is frozen. Chest overflow is refused rather than dropping items. Crop growth progress is ephemeral and is not saved. There is no saturation, and no water or fertilizer farming.
