| D004 |  | architecture | M001 slice ordering | Four slices in risk order: S01 winit ApplicationHandler migration and S02 settings core run first (independent, can run in parallel), then S03 UI foundation (depends on S01), then S04 settings menu (depends on S02+S03) as the end-to-end integration slice. | The two independent risk-retiring foundations come first: the winit migration is the highest integration risk (every input path changes, gated by manual smoke check) and the settings core is pure logic delivering the crate's first tests. | D005 |  | architecture | S02 settings TOML load strategy: two-phase per-field fallback vs serde-default derive | Load settings.toml via a two-phase parse: `toml::from_str::<toml::Value>` first (fails only on syntactically invalid TOML -> all defaults), then per-field extraction with type/range checks per field; save via a private Serialize-only serde mirror struct. Do not load via `#[serde(default)]` derive on the Settings struct. | Per-field fallback (a valid field survives an invalid sibling, out-of-range values clamp with warnings instead of aborting) is the milestone requirement "a bad settings.toml never blocks launch", and serde derive aborts the whole struct on any field type error. The two-phase approach gives exactly the required fallback granularity; the Serialize-only mirror keeps the saved file format clean and stable while load logic stays hand-checked. | Yes | agent |
| D006 |  | architecture | S02 settings observability: warnings and keybind conflicts as returned data vs logging framework | Return load warnings and keybind conflicts as data: `load_with_warnings(path) -> (Settings, Vec<SettingsWarning>)` with a thin `Settings::load` wrapper, and `validate_keybinds() -> Vec<KeybindConflict>` shared by load (warn, never block) and S04's rebind flow (reject duplicates). Do not add a log/tracing dependency in S02. | The crate has no logging dependency at all; introducing one in this slice expands scope and forces a logger choice S04 doesn't need yet. Warnings are decision-point data (which field fell back and why) that S04 must display in the settings menu, so structured return values are the right interface — one validate function serves both the load-time warning and the rebind-time rejection call sites, testable without UI. | Yes | agent |
| D007 |  | architecture | S03 UI render-pass seam: how the glyphon/quad UI pass draws between the world pass and present | Add an optional UI pass hook to render_frame: a `ui_pass: Option<&mut dyn FnMut(&mut wgpu::RenderPass)>` parameter that, when Some, opens a second begin_render_pass on the existing encoder — color-only (no depth_stencil_attachment), LoadOp::Load on the color attachment, same view — between the world pass and queue.submit + output.present. Do not split render_frame into separate world/render phases and do not create a second surface texture or encoder. | Least-churn seam into the existing submit-and-present-inside-method structure: the world pass, camera uniform, overlay line drawing, and the build_overlay_line_vertices unit test all stay untouched, while the hook gives src/ui a color-only pass on the same encoder and texture before present — glyphon's TextRenderer (depth_stencil None) and quads can share it, and S04's menu draws through the same hook. A full render_frame split would churn every call site for no added capability. | Yes | agent |
